# **FastAPI Middleware Architecture & Scoping Document**

This document synthesizes the overarching architectural blueprints into a focused scope specifically for the FastAPI backend layer. It outlines the role of FastAPI as the central orchestrator (the "Bouncer" and "Brain") between the physical edge hardware (ESP32), the presentation layer (Next.js), the database (Supabase), and the local AI processing pipeline (Gemma E2B).

## **1\. The Role of FastAPI in the Architecture**

The system utilizes a Decoupled (Headless) Architecture. The frontend (Next.js) acts as a pure presentation layer, and the ESP32 acts as a localized messenger. The FastAPI backend is the central authority, responsible for all heavy lifting, business logic, security, and data orchestration.

* **Decoupling & Scalability:** FastAPI treats the Next.js frontend and the ESP32 scanner as equal HTTP clients. This allows for seamless scaling (e.g., adding a mobile app later) without rewriting backend logic.  
* **Security (The Bouncer):** Middleware protects the API by intercepting requests, enforcing CORS (Cross-Origin Resource Sharing), checking authentication tokens, and rate-limiting. This prevents unauthorized access and protects the backend from being flooded with requests.  
* **Logic Protection:** By centralizing logic in the backend, sensitive information like AI prompts, admin overrides, and API keys remain hidden from the frontend and potential attackers.  
* **Data Orchestration:** FastAPI acts as the gateway to the Supabase database. It prevents the frontend from bypassing business logic or audit logging by ensuring all mutations go through the API.

## **2\. Middleware Implementation Scope**

Middleware in FastAPI acts as the first line of defense, intercepting requests before they reach the core business logic. The following middleware components will be implemented:

* **Middleware Component:** CORS (Cross-Origin Resource Sharing)  
  * **Purpose & Functionality:** Defines which external domains (e.g., the Next.js Vercel deployment) are permitted to communicate with the API. It blocks unauthorized cross-origin requests.  
* **Middleware Component:** Authentication / JWT Validation  
  * **Purpose & Functionality:** Intercepts requests requiring authorization to verify the presence and validity of Admin Tokens or API keys. Rejects unauthorized access before hitting the database.  
* **Middleware Component:** Rate Limiting (Anti-Spam)  
  * **Purpose & Functionality:** Tracks the frequency of requests from specific IP addresses. It enforces cooldowns and protects the server from spam (e.g., rapid, repeated ESP32 pings) by returning a 429 Too Many Requests error.  
* **Middleware Component:** Global Request Logging  
  * **Purpose & Functionality:** Logs the timestamp, IP address, and request path for every incoming connection, providing a comprehensive audit trail for diagnostics and security monitoring.

## **3\. Core Route Implementation Scope (The Brain)**

Once middleware validates a request, it is passed to the specific API routes where the actual business logic, database mutations, and AI processing occur.

### **3.1. Hardware Integration Routes (ESP32)**

* **POST /api/v1/time-in (and time-out):** Receives raw UID data from the ESP32.  
* **Business Logic:** Queries Supabase to match the UID to an employee. Applies "Business Cooldowns" (e.g., a 5-minute rule between Time In and Time Out) to prevent accidental or malicious spamming.  
* **Response:** Returns a structured JSON payload to the ESP32 (e.g., {"status": "success", "employee_name": "John Doe", "message": "Time In: 09:10 AM"}) for real-time display on the OLED screen.  
* **Performance:** Designed for sub-100ms response times to ensure instant visual feedback on the edge hardware.

### **3.2. Administrative Override Routes (Next.js)**

* **POST /api/v1/admin/override:** Handles manual Time-In/Time-Out entries or deletions from the HR dashboard.  
* **Business Logic:** Enforces the rule that *all* data modifications must pass through FastAPI. This route validates data, performs necessary calculations (e.g., recalculating total hours), and writes to an audit_logs table before mutating the Supabase records.  
* **Soft Deletion:** Implements soft deletes (e.g., setting an is_deleted = true flag) rather than hard-deleting records to preserve data integrity and audit history.

### **3.3. AI & Analytics Orchestration Routes (Gemma & pgvector)**

* **GET /api/v1/analytics/query:** Receives natural language queries from the React dashboard (e.g., "Show me employees showing signs of burnout.").  
* **RAG Pipeline Execution:** Embeds the query into a vector, queries Supabase pgvector for relevant employee summaries, and passes the context to the local Gemma 4 E2B model.  
* **Response:** Returns the synthesized, natural-language HR report generated by Gemma back to the frontend.  
* **Background Processing:** Utilizes FastAPI BackgroundTasks to offload heavy AI computation (like daily anomaly detection roll-ups), ensuring the API remains responsive. Triggers Server-Sent Events (SSE) to push alerts to the frontend if anomalies are detected.

## **4\. Fallback and Resilience Scope**

* **Hardware Debounce (Edge Level):** The ESP32 firmware includes a localized debounce timer (e.g., ignoring repeated scans within 2 seconds) to prevent flooding the local network before the request even reaches the FastAPI middleware.  
* **Health-Check Endpoint:** A dedicated /health-check route allows the system to monitor API uptime and trigger alerts if the server or database connection drops.

# **AI-Powered Workforce Management Architecture**

This document serves as the master blueprint and reference guide for the capstone project. It details the complete end-to-end integration of edge hardware, server infrastructure, relational/vector databases, and the local AI processing pipeline. The architecture is explicitly designed to decouple tasks, allowing distributed development across team members.

## **1\. Core Submodules Overview**

The system is divided into operational submodules, with the AI analytics engine acting as the central nervous system automating insights across the board.

* **Time and Attendance System:** Handles raw hardware taps, real-time logging, and state synchronization.  
* **Shift and Schedule Management:** Defines expected working hours against which the AI calculates lateness and absences.  
* **Timesheet Management:** Aggregates raw tap data into payroll-ready formats.  
* **Leave Management:** Tracks planned absences so the AI does not flag an employee as AWOL.  
* **Workforce Analytics (The Brain):** The central RAG pipeline running Gemma to deduce patterns, flag dips, and predict future trends.  
* **Performance & Development:** Generates actionable feedback for HR based on the analytics output.

## **2\. Hardware Layer (The Edge Node)**

The hardware acts as a standalone IoT device. It requires no continuous management other than a 5V power source and a local Wi-Fi connection.

&nbsp;

* **Component:** ESP32 Development Board  
  * **Function:** Microcontroller / Wi-Fi Brain  
  * **Integration Detail:** Connects to Wi-Fi, parses RFID data, sends HTTP POST to the backend API.  
* **Component:** RC522 RFID Module  
  * **Function:** Data Ingestion  
  * **Integration Detail:** Reads the unique UID of the 13.56MHz IC cards tapped by employees.  
* **Component:** 1.3-inch OLED (SH1106)  
  * **Function:** Visual Feedback  
  * **Integration Detail:** Displays "TIME IN" or "TIME OUT" along with employee names to provide physical verification.  
* **Component:** Active Buzzer Module (3.3V)  
  * **Function:** Audio Feedback  
  * **Integration Detail:** Triggered via a single digital HIGH signal to emit an instant validation beep.

## **3\. Server & Networking Infrastructure**

The backend is deployed on a dedicated Linux server, ensuring maximum control over data and AI execution environments.

* **DNS & Routing:** A dedicated subdomain (e.g., attendance.canefly.xyz) routes edge traffic directly to the server.  
* **Reverse Proxy:** It uses a Cloudflare Tunnel strategy to bypass manual Nginx configuration and keeps the hardware off the public internet.  
* **API Gateway:** Python FastAPI acts as the traffic controller. It uses BackgroundTasks to offload heavy AI computation, allowing it to instantly return a 200 OK status to the ESP32.  
* **Process Management:** The API is managed by systemd to ensure high availability and automatic restarts on failure.

## **4\. Database Architecture: Supabase & pgvector**

Supabase serves as both the relational data store and the vector database, eliminating the need for fragmented infrastructure.

* **Raw Logs Table:** Captures high-frequency, low-latency timestamp data directly from the FastAPI endpoint.  
* **Roll-up Aggregation:** Python scripts periodically compute basic metrics (e.g., average time-in, total leaves).  
* **Vector Store (pgvector):** Text-based summaries generated by the AI are converted into embeddings and stored alongside relational data, enabling sub-millisecond similarity searches.

## **5\. AI & RAG Pipeline (Gemma E2B)**

The analytics engine utilizes the local Gemma 4 E2B model (2.3B effective parameters, 128K context window) to perform complex reasoning without bottlenecks.

&nbsp;

```
# Example RAG Workflow:
1. Admin queries the React dashboard: "Show me employees showing signs of burnout."
2. The query is embedded into a vector.
3. Supabase pgvector retrieves the top 5 most relevant employee AI summaries.
4. FastAPI passes the query and the 5 summaries into Gemma's context window.
5. Gemma outputs a synthesized, natural-language HR report.
```

For proactive triggers, Gemma runs in the background analyzing the daily roll-ups. If an anomaly is detected (e.g., a massive performance dip), FastAPI pushes a Server-Sent Event (SSE) directly to the React frontend to alert management.

## **6\. The Frontend Architecture**

The client application is built using a Next.js App Router monorepo and will be deployed to Vercel, styled with Tailwind CSS. It is entirely decoupled from the AI and Hardware, consuming data strictly through the Python FastAPI layer.

**Responsibilities:** Rendering the dashboard, visualizing Timesheet/Leave data, rendering the real-time SSE notifications, and providing the search interface for the RAG analytics engine.

# **Capstone Architecture & Edge Node Blueprint**

This document serves as the master blueprint for the Enterprise Resource Planning (ERP) capstone project. It outlines the scope, hardware specifications, and system architecture required to integrate a physical IoT edge node (RFID scanner) with a Next.js frontend, a Supabase database, and a locally hosted Agentic AI backend.

## **Part 1: Physical Hardware & Edge Node (RFID Scanner)**

The edge node acts as the physical entry point for the system. It captures employee attendance via NFC/RFID and transmits the payload directly to the custom API.

### **Hardware Component Specifications**

&nbsp;

* **Component:** ESP32 Development Board  
  * **Purpose & Technical Notes:** The core microcontroller processing Wi-Fi HTTP POST requests. Runs at room temperature (no heatsink required). Does not require an expansion shield for the final build.  
* **Component:** RC522 RFID Module  
  * **Purpose & Technical Notes:** Scans NFC tags. **CRITICAL:** Must be wired strictly to 3.3V power. Connecting to 5V will permanently damage the module.  
* **Component:** 1.3-inch OLED Screen  
  * **Purpose & Technical Notes:** Visual feedback display (e.g., "Access Granted", timestamps, custom boot animations).  
* **Component:** Blank IC Cards (NFC)  
  * **Purpose & Technical Notes:** High-frequency 13.56 MHz cards. Capable of carrying NDEF payloads, meaning they can function as smart business cards scannable by modern iOS devices.

### **Wiring & Assembly Strategy**

* **Prototyping Phase:** Utilize an 830-tie-point breadboard with a mix of Male-to-Male (M2M) and Male-to-Female (M2F) dupont wires to distribute 3.3V and GND rails.  
* **Color-Coding Standard:** Red (3.3V Power), Black (Ground/GND), and Green/Blue/Yellow (SPI Data/I2C).  
* **Final Assembly:** Remove the breadboard to shrink the physical footprint. Use Female-to-Female (F2F) jumper wires directly connecting the ESP32 pins to the peripheral modules. Secure the F2F connections with hot glue for a solderless, non-destructive grip.

### **Enclosure Design**

To achieve a premium, minimalist aesthetic, the enclosure will be constructed from precisely cut foamboard. To avoid chemical melting caused by aerosol spray paints, the exterior will be finished with a texture-mapped sticker paper wrap or a matte black vinyl skin.

## **Part 2: Full-Stack System Architecture**

The software ecosystem utilizes a "Thin Client / Fat Server" architecture, pushing all heavy business logic and AI orchestration to a secure backend while keeping the frontend strictly for presentation.

### **1\. The Thin Client (Next.js Monorepo)**

* **Framework:** Next.js App Router handling 7 different enterprise departments.  
* **Routing Strategy:** Utilize Route Groups (e.g., (hr), (fleet)) to isolate departmental codebases.  
* **Version Control:** Strict Feature Branching (e.g., feature/backend-ai) with pull requests merging into a develop branch to avoid direct-to-main merge conflicts.  
* **Deployment:** Hosted on Vercel (Hobby Tier) to offload bandwidth and CPU processing from local hardware.

### **2\. The Gateway (FastAPI Backend)**

* **Role:** Acts as the orchestrator and traffic cop. Intercepts raw RFID pings, applies business logic (e.g., schedule validation), and triggers the AI models before communicating with the database.  
* **Hosting:** Deployed locally on a Small Form Factor (SFF) Linux PC. Exposed securely to the Vercel frontend via a Cloudflare Tunnel at api.canefly.xyz.  
* **Middleware:** Enforces security, intercepts requests to apply custom logging, and handles state mutations.

### **3\. The Database (Supabase)**

* **Domain-Driven Design:** A single, unified PostgreSQL database handles the entire ERP system, allowing seamless \`JOIN\` queries across HR, Payroll, and Performance tables.  
* **Security:** All pgvector embeddings and AI logs are isolated in a custom ai_analytics schema. The FastAPI backend accesses this via the Service Role Key, hiding it from general frontend CRUD operations.  
* **Storage Limits:** To preserve the 500 MB database tier, all large assets (like profile pictures) will be uploaded to Supabase Storage, with only their URL strings saved in the Postgres tables.

### **4\. The AI Engine (Agentic Orchestration)**

The system utilizes Agentic AI through standardized "Function Calling" (tool use). By relying on standard JSON schemas, the backend achieves Vendor Lock-In Immunity, allowing seamless swapping between the local uncensored Gemma E4b model and cloud flagship models (e.g., Gemini Flash, Claude).

&nbsp;

```json
// Example Fine-Grained Permission Schema to prevent token drain
{
  "deny": ["read_file(src/app/(fleet)/*)"],
  "allow": ["write_file(src/app/(hr)/*)"],
  "ask": ["mutate_database_schema"]
}
```

## **Part 3: Graceful Degradation & Defense Day Fail-safes**

To ensure a flawless panel presentation, the system is engineered with strict fallback protocols:

* **Network Drops:** If the ESP32 fails to connect to the Wi-Fi or API, it triggers a visual error state on the OLED screen, preventing silent failures.  
* **Hardware Nuke Contingency:** If the physical edge node is destroyed or loses power, the Next.js HR dashboard features a "Manual Override" Time-In/Time-Out button for manual data entry.

**Telemetry & Uptime Monitoring:** The FastAPI server maintains a /health-check endpoint. If the edge node drops off the network, the dashboard alerts the HR admin immediately.
